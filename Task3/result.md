# Задание 3. Переход на Event-Driven архитектуру

## Cписок проблем, которые связаны с планируемым ростом нагрузки

* ___ins-product-aggregator___ работает синхронно со сторонними API и зависит от них, возможны сбои при обращении и как следствие - потеря данных
* при увеличение сторонних api количество сбоев ___ins-comp-settlement___ будет увеличиваться
* ___ins-comp-settlement___ раз в сутки создает большую нагрузку
* При изменении предложений СК ___ins-comp-settlement___ узнает об этом только при следующем обновлении, которое происходит раз в сутки - есть риск получить неактуальные данные

## Предлагаемые зешения

* добавить Circuit Breaker на подключение к каждому внешнему api, при этом в аггрегированной информации по предложениям необходимо добавить маркер недоступности СК. Это поможет избежать проблемы неактуальных страховок.
* добавить очередь (Apache kafka)
* ___ins-product-aggregator___ будет создавать сообщения о событии обновления предложений СК, которые он будет получать по расписанию.
* ___ins-comp-settlement___ и ___core-app__ будут в качестве подписчиков читать сообщения о событии обновления предложений СК и при наличии реальных изменений будут обновлять записи в своих БД.
* внедрение Transactional Outbox не имеет смысла, так как потеря сообщения об обновлении предложений не является критичной, т.к. вызовет только не значительную задержку в предоставление данных, а так же при перезапуске сервисов ins-comp-settlement или core-app будет возможность перечитать сообщения из топика kafka и восстановить актуальные предложения СК.
* Передача данных об оформленных страховках из __core-app__ в __ins-comp-settlement__ критически важна(т.к. каждое такое событие непосредственно приносит прибыль компании).
Для того что бы гарантировать доставку таких сообщений используется CDC система Debezium, которая читает лог ___postgres core-db___ и генерирует сообщения о событие оформеление страховки в топик kafka.
* ___ins-comp-settlement___ подписывается на сообщения об оформлении страховок и плавно накапливает данные в своей БД для суммарных отчетов.
